# Feature Specification: Local Ollama LLM Provider

**Feature Branch**: `002-add-ollama-provider`

**Created**: 2026-08-18

**Updated**: 2026-08-18 — added automatic local-model provisioning (User Story 4) so a normal deployment startup no longer requires a separate manual model-download step.

**Status**: Draft

**Input**: User description: "Extend Albercik Chatbot with a local Ollama LLM provider. Allow the existing RAG chatbot to use either Anthropic Claude or a locally running Ollama model without changing the core RAG pipeline, selected via server-side configuration only, with all existing abuse/cost/security controls preserved identically across both providers." Addendum: "The system must automatically ensure that the configured local model is available before the application starts using it — a normal deployment startup should not require the operator to manually trigger a model download."

## Clarifications

### Session 2026-08-18

- Q: When LLM_PROVIDER isn't explicitly set, which backend should the system use by default? → A: ollama — the local backend is the default; Anthropic must be explicitly selected via configuration.
- Q: When the local model backend fails with a transient error (timeout, connection refused), should the system retry before giving up? → A: Bounded retries — mirrors the existing Anthropic pattern (a small, bounded number of attempts, then the safe "unavailable" outcome).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Operator runs the chatbot on a local model instead of a paid API (Priority: P1)

An operator deploying or running Albercik Chatbot wants to answer questions using a locally-hosted open-source model instead of the paid Anthropic API — for example during development, for offline use, or to avoid per-question cost — without touching any application code.

**Why this priority**: This is the entire point of the feature. Without it, there is no alternative to the paid provider at all, and the feature delivers no value.

**Independent Test**: With the chatbot's answer-generation backend set to the local model via configuration only, ask an in-scope, knowledge-base-covered question through the public chat endpoint and confirm a grounded answer comes back, with no code changes and no calls to the paid provider.

**Acceptance Scenarios**:

1. **Given** the chatbot is configured to use the local model backend, **When** a visitor asks a question the knowledge base covers, **Then** the chatbot returns a grounded answer generated by the local model, and no request is made to the paid provider.
2. **Given** the chatbot is configured to use the local model backend, **When** an operator inspects usage records, **Then** those records are clearly attributable to the local model backend, not the paid provider.

---

### User Story 2 - Operator switches backends with configuration only, protections unchanged (Priority: P2)

An operator who has been running on the paid provider switches the configured backend to the local model (or back again) purely by changing configuration, and needs full confidence that every existing abuse, cost, and security protection — rate limiting, concurrency limits, request/context/output size limits, the kill switch, prompt-injection defenses, and scope control — still applies exactly as before, regardless of which backend is answering.

**Why this priority**: A configurable backend that quietly weakens existing protections is worse than no configurability at all — this is what makes the feature safe to actually use.

**Independent Test**: With each backend selected in turn (no code changes between runs), exercise the existing abuse/cost/security test scenarios (rate limit exceeded, kill switch on, budget exhausted, oversized request, prompt-injection attempt) and confirm identical outcomes in both configurations.

**Acceptance Scenarios**:

1. **Given** the chatbot is configured to use the paid provider, **When** the operator changes only the backend-selection configuration value and restarts, **Then** the chatbot now answers using the local model with no code changes required.
2. **Given** either backend is configured, **When** a visitor exceeds the rate limit, sends an oversized question, or attempts a prompt-injection message, **Then** the outcome (rejection, safe refusal, no leaked internal detail) is identical regardless of which backend is configured.
3. **Given** the local model backend is configured, **When** requests are made through it, **Then** the paid provider's monetary/usage budget is not reduced or affected in any way.
4. **Given** a request body attempts to specify which backend or model should answer, **When** the request is processed, **Then** the attempt has no effect — the backend is determined exclusively by server-side configuration.

---

### User Story 3 - Operator compares answer quality between backends (Priority: P3)

An operator or evaluator wants to run the same fixed set of evaluation questions against both the paid provider and the local model to compare how each performs, before deciding which to use for a given deployment.

**Why this priority**: Valuable for decision-making once the first two stories work, but the feature is still useful with only manual backend switching and no formal side-by-side comparison tooling.

**Independent Test**: Run the existing evaluation question set against the chatbot once per backend (switching only configuration between runs) and confirm both runs produce directly comparable, backend-labeled results using the same question set and expected outcomes.

**Acceptance Scenarios**:

1. **Given** the same fixed evaluation question set, **When** it is run once against each configured backend, **Then** both runs produce results (outcome per question, pass/fail against the same expectations) that can be compared side by side.

---

### User Story 4 - Operator gets a fully working local backend from a single startup command (Priority: P2)

An operator starting the chatbot's deployment stack for the first time (or after stopping and starting it again) wants the configured local model to be ready automatically, without having to remember or separately run a manual model-download command before the chatbot can actually answer anything through the local backend.

**Why this priority**: Without this, User Story 1's "just works" local-backend promise silently fails on a normal first run — the deployment starts successfully but every local-backend request returns "unavailable" until the operator discovers and runs an undocumented manual step. This story is what makes User Story 1 actually deliver on its promise for a normal deployment, so it carries the same priority as User Story 2.

**Independent Test**: On a machine with no previously-downloaded local models, start the deployment stack configured to use the local backend using only the single documented startup command, wait for the stack to report ready, then ask an in-scope question through the public chat endpoint and confirm a grounded answer — with no manual model-download command run at any point.

**Acceptance Scenarios**:

1. **Given** a fresh environment with the local backend configured and no model previously downloaded, **When** the operator runs the single documented startup command, **Then** the configured model is automatically made available before the chatbot begins serving local-backend requests, with no separate manual download command required.
2. **Given** the configured model was already downloaded in a previous run and its persisted storage was not removed, **When** the operator stops and starts the stack again, **Then** the model is not re-downloaded, and startup is not meaningfully slowed by a redundant download.
3. **Given** the operator changes which model is configured, **When** the stack is next started, **Then** the newly configured model — not the previous one — is the one made available, without any application code change.
4. **Given** the configured model cannot be made available (for example, the local service cannot reach its model source, or the configured model identifier is invalid), **When** startup is attempted, **Then** the failure is visible in the startup output, the chatbot's local-backend-serving path does not proceed as though the model were ready, and no request is silently routed to a different backend as a substitute.
5. **Given** the operator has previously run the stack and later explicitly removes the local model's persisted storage, **When** the stack is started again, **Then** the model is treated as not present and is downloaded again automatically.

---

### Edge Cases

- What happens when the local model backend is configured but the local model service isn't running or isn't reachable? → Visitor receives the existing safe "unavailable" response; no connection details, hostnames, or stack traces are exposed.
- What happens when the local model backend is reachable but the configured model isn't available on it? → Same safe "unavailable" response as any other backend failure.
- What happens when the local model backend accepts the request but doesn't respond before the configured timeout? → Treated as a provider failure; safe "unavailable" response, no indefinitely hanging request.
- What happens when the local model backend returns a response that doesn't match the expected shape? → Treated as a provider failure; safe "unavailable" response, nothing malformed is passed through to the visitor.
- What happens when a request body includes fields attempting to choose a provider, model, or generation parameters? → Silently has no effect; those values are controlled exclusively by server-side configuration, exactly as already true for the paid provider today.
- What happens to content generated by the local model that contains instruction-like text (prompt injection via a compromised or unusual local model response)? → Handled with the same untrusted-output treatment already applied to paid-provider output — no elevated trust is given to local-model content.
- What happens when the local model service process itself is still starting up (not yet accepting requests) at the moment automatic model provisioning begins? → Provisioning waits for the service to become ready rather than failing immediately on a transient not-ready state.
- What happens when the configured model identifier doesn't exist or is misspelled? → Automatic model provisioning fails visibly; the chatbot's local-backend-serving path does not start as though a model were ready, and no silent substitution of a different backend occurs.
- What happens when the paid provider (not the local backend) is the configured backend for a given deployment? → No automatic model provisioning behavior is required for that deployment; this story only applies while the local backend is the one actually configured.
- What happens when the local model service is configured to use hardware acceleration? → Automatic model provisioning behaves the same either way; acceleration is a property of the local model service only, never of the provisioning step itself.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST support two interchangeable answer-generation backends — the existing paid provider and a locally-hosted model backend — behind the same internal abstraction, so the rest of the question-answering flow does not need to know which one is active.
- **FR-002**: The active backend MUST be selected exclusively by server-side configuration; no request from a Public User, Administrator, or any client MUST be able to select, override, or influence which backend or model answers a given question.
- **FR-003**: The backend-selection configuration MUST have an explicit, documented default value (the local model backend) rather than depending on the presence/absence of other settings to infer which backend is active; this default MUST be documented prominently enough that an operator upgrading an existing paid-provider deployment understands they must explicitly select the paid provider to keep today's behavior.
- **FR-004**: Switching the configured backend (in either direction) MUST require a configuration change only — no code change of any kind.
- **FR-005**: The existing paid-provider backend MUST remain fully supported and unremoved; adding the local backend MUST NOT degrade or alter its existing behavior.
- **FR-006**: The local model backend's connection location and model name MUST be independently configurable, with reasonable documented development defaults, rather than hardcoded anywhere in the core question-answering logic.
- **FR-007**: Core question-answering logic (retrieval, scope determination, context assembly, response shaping) MUST behave identically regardless of which backend is configured — no backend-specific branching outside the backend implementations themselves.
- **FR-008**: The local model backend's network endpoint MUST NOT be reachable by public website visitors under any deployment configuration intended for real use; it MUST only be reachable by the application itself.
- **FR-009**: All existing abuse and cost controls — rate limiting, concurrency limits, question-length and request-size limits, retrieved-context size limits, output-length limits, the kill switch, prompt-injection defenses, and scope control — MUST apply identically to a chat request regardless of which backend answers it.
- **FR-010**: Paid-provider monetary/usage budget enforcement MUST continue to apply only to paid-provider usage; usage served by the local model backend MUST NOT count toward, reduce, or be able to exhaust that budget.
- **FR-011**: Usage accounting MUST record which backend served each request, so paid-provider and local-model usage remain distinguishable after the fact.
- **FR-012**: Usage accounting for the local model backend MUST capture latency and token counts when the backend itself reports them, without requiring them to be present when it doesn't.
- **FR-013**: When the local model backend is unreachable, refuses a connection, is missing the configured model, times out, or returns a response that cannot be understood, the system MUST produce the same safe "unavailable" outcome already used for other backend failures — never exposing internal network addresses, configuration, or technical error detail to the visitor.
- **FR-014**: The local model backend MUST retry a transient failure (timeout, connection error) a small, bounded number of times before giving up, mirroring the existing paid-provider retry behavior — never retrying without bound, and never retried again by any other layer once it has given up.
- **FR-015**: Content produced by the local model backend MUST be treated as untrusted output, subject to the same handling as paid-provider output, never granted elevated trust.
- **FR-016**: The existing fixed evaluation question set MUST be runnable against either configured backend without modification to the question set itself, producing results that identify which backend produced them.
- **FR-017**: The automated test suite MUST be able to run in full, without requiring the local model backend to be installed, running, or reachable.
- **FR-018**: On startup, the system MUST record server-side (never client-visible) which backend and which model are active, so an operator can confirm the running configuration without inspecting environment variables directly; this record MUST NOT include credentials, API keys, or internal network addresses/URLs.
- **FR-019**: When a deployment's local backend is configured, the system MUST make the configured model available automatically as part of normal deployment startup, without requiring the operator to run a separate manual model-download command.
- **FR-020**: Automatic model provisioning MUST wait until the local model service itself is ready to accept requests before attempting to ensure the configured model is available, rather than failing on a transient not-yet-ready state.
- **FR-021**: Automatic model provisioning MUST use the same single, configured model identifier that the local backend uses at request time — never a separately hardcoded or duplicated model name.
- **FR-022**: If the configured model is already present in the local backend's persisted storage, automatic model provisioning MUST NOT re-download it.
- **FR-023**: The chatbot MUST NOT begin serving local-backend requests as though the model were ready until automatic model provisioning has completed successfully.
- **FR-024**: Downloaded local-model data MUST be kept in storage that persists across a normal deployment stop/start cycle; it MUST be lost only when the operator explicitly removes that persisted storage.
- **FR-025**: Automatic model provisioning MUST run as a distinct, one-shot startup step, separate from the chatbot application's own request-handling code, so provisioning logic never becomes part of core application/domain logic.
- **FR-026**: The local model service's endpoint used for automatic provisioning MUST remain reachable only from within the deployment's internal network; provisioning MUST NOT require exposing that endpoint publicly.
- **FR-027**: Automatic model provisioning MUST NOT require adding authentication credentials beyond whatever a concrete deployment environment already needs.
- **FR-028**: If the configured model cannot be made available (download failure, invalid model identifier, or similar), automatic model provisioning MUST fail visibly in the startup process output; the chatbot MUST NOT proceed as though the model were ready, and MUST NOT silently substitute a different backend in its place.
- **FR-029**: Automatic model provisioning MUST behave the same way whether or not the local model service is configured to use hardware acceleration; the provisioning step itself MUST NOT require that acceleration.
- **FR-030**: The automated test suite MUST remain runnable in full without requiring a real local model service to be running and without downloading any real model.

### Key Entities

- **Backend Selection**: A server-side configuration decision (not visitor-controlled, not persisted per-request) determining which of the two supported answer-generation backends handles a given moment in time; has an explicit default.
- **Usage Record** *(extends the existing concept)*: Each recorded unit of provider usage now also identifies which backend (paid provider vs. local model) it belongs to, so paid-provider budget logic can continue to consider only paid-provider records.
- **Model Provisioning Step**: A one-shot, startup-time operational action — never triggered by visitor input, never part of per-request handling — that ensures the currently-configured local model is present before the chatbot serves any local-backend traffic; distinct from, and a prerequisite to, the chatbot's own request-handling startup.

### Out of Scope

- Any additional agent framework or orchestration layer (e.g. LangChain, LangGraph) or autonomous agent behavior.
- Any additional vector database or retrieval store beyond what already exists.
- Using the local model backend for embeddings — it is a source of generated answers only; embedding generation is unaffected by this feature.
- Automatic fallback or routing between backends (e.g. trying the local backend if the paid one fails, or load-balancing between them) — exactly one backend is active at a time, by explicit configuration.
- GPU scheduling/orchestration or any container-orchestration platform beyond what's already used for this project.
- Automatic selection of which model to use — the model to provision remains an explicit configuration choice, never inferred or chosen by the system.
- Managing or orchestrating more than one local model at a time.
- Triggering a model download in response to public visitor input or at question-answering request time.
- Any model source or registry beyond the local model service's own normal model-fetch mechanism.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can switch the chatbot's answer-generation backend by changing a single configuration value and restarting, with zero code changes.
- **SC-002**: Every existing abuse, cost, and security protection produces the same observable outcome (accept/reject, safe message, no leaked detail) regardless of which backend is configured, verified across both configurations.
- **SC-003**: When the local model backend is unavailable for any reason, a visitor's request still completes within the existing bounded response time and receives the same safe, non-technical "temporarily unavailable" message already used for other outages — never a hang, crash, or exposed technical detail.
- **SC-004**: The same fixed evaluation question set can be run once per backend and produce directly comparable, backend-labeled pass/fail results without modifying the question set.
- **SC-005**: While the local model backend is the configured backend, paid-provider usage and budget consumption remain at zero for requests served locally.
- **SC-006**: The full automated test suite passes without the local model backend being installed or running anywhere in the test environment.
- **SC-007**: An operator can confirm which backend and model are active by reading server startup output alone, without inspecting configuration files or environment variables directly, and that output never contains a credential or an internal network address.
- **SC-008**: An operator can go from a completely fresh environment to a working local-backend chatbot using a single documented startup command, with no separate manual model-download step.
- **SC-009**: Stopping and starting the deployment again, without removing persisted local-model storage, does not re-download the model and does not meaningfully increase startup time compared to the model already being present.
- **SC-010**: When the configured model cannot be made available, this is visible in startup output, and the chatbot never silently serves local-backend requests as though it were ready, and never silently answers via a different backend instead.

## Assumptions

- The default backend, absent any explicit configuration, is the local model backend — a fresh deployment works without any paid-provider credentials. Anyone who wants the paid provider (including existing deployments upgrading into this feature) MUST explicitly select it via configuration.
- Running the local model backend's own runtime/software (the service process itself) remains an operational/deployment responsibility of whoever runs a given deployment; this feature is responsible only for ensuring the *configured model* is present inside an already-running local model service, not for installing or managing that service's software.
- Automatic model provisioning relies on the local model service already offering a standard way to check for and fetch a model by name (its own normal model-fetch mechanism); this feature does not implement a separate model registry or download protocol of its own.
- "Locally-hosted" may mean the local model backend runs on the same host as the application or as a separate service reachable only over an internal/private network — both are acceptable operator choices, not something the feature needs to decide for them.
- No automatic fallback or routing between backends is required or wanted; exactly one backend is active at a time, by explicit operator choice. This now also holds during startup: if the configured model cannot be provisioned, the system fails visibly rather than falling back to the paid provider.
- Answer quality/behavior differences between the two backends are expected and are evaluated via the existing evaluation question set, not engineered around within this feature.
- The specific initial local model choice is a starting recommendation, not a fixed requirement — the model in use must remain a configuration value, not a hardcoded assumption anywhere in behavior, including in automatic model provisioning.
