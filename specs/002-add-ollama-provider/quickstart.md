# Quickstart: Local Ollama LLM Provider

Validates this feature end-to-end against `spec.md`'s acceptance scenarios.
Assumes the base `001-albertos-rag-chatbot` quickstart has already been
completed at least once (database migrated, an Administrator account exists).

## Prerequisites

- Everything from `specs/001-albertos-rag-chatbot/quickstart.md`.
- Docker Compose (the `ollama` and `ollama-init` services are part of the
  default stack — research.md §6, §6a).
- No new secrets: Ollama's local API needs no API key.
- Enough disk space and network access for a one-time model download the
  first time you start the stack (see Scenario 4, step 5 below for what
  happens without it).

## Setup

```bash
uv sync
uv run alembic upgrade head        # applies the new usage_records.provider_name column
docker compose up -d               # brings up `ollama`, waits for it to be
                                    #   healthy, then `ollama-init` ensures
                                    #   OLLAMA_MODEL is present, then `app`
                                    #   starts — no separate manual step
curl localhost:8000/health
```

**Expected**: `{"status": "ok"}`. `LLM_PROVIDER` is unset in `.env`, so the
default (`ollama`, per the Clarifications session) is active, and the
configured model (`OLLAMA_MODEL`, default `qwen3:4b`) was downloaded
automatically before `app` started — no `ollama pull` command was run by
hand. On a fresh machine, `docker compose up -d` returning (i.e. `app`
actually starting) confirms `ollama-init` already finished successfully,
since `app` will not start otherwise (spec FR-023).

### Where the model is stored, and what survives a restart

- Downloaded model data lives in the named Docker volume `ollama-data`
  (mounted at `/root/.ollama` in the `ollama` service).
- `docker compose down` followed by `docker compose up -d` reuses that
  volume — `ollama-init` finds the model already present and does not
  re-download it (spec FR-022; confirm via `docker compose logs
  ollama-init`, which prints something like `already exists` almost
  immediately rather than showing download progress).
- `docker compose down -v` removes the volume along with everything in
  it — the next `docker compose up -d` downloads the model again from
  scratch, exactly like a fresh environment.

### Changing the configured model

Set `OLLAMA_MODEL` in `.env` (e.g. `OLLAMA_MODEL=qwen3:8b`) and run
`docker compose up -d` again. `ollama-init` ensures the newly configured
model specifically — not the previous one — without any application code
change (spec FR-021); the previous model's data remains in the volume
unless removed separately.

### Alternative: Ollama running on the host instead of in Docker

If you already run Ollama natively (not in a container), set, before
`docker compose up -d`:

```bash
# .env
OLLAMA_BASE_URL=http://host.docker.internal:11434
```

(Docker Desktop / WSL2 resolve `host.docker.internal` to the host machine;
on native Linux Docker you may need the host's real LAN/bridge address
instead.) In this setup the Compose-managed `ollama`/`ollama-init`
services are unused; provision the model on the host directly with
`ollama pull qwen3:4b` (or whatever `OLLAMA_MODEL` is set to) before
starting the stack, since automatic provisioning only manages the
Compose-internal `ollama` service.

## Scenario 1 — Local model answers a grounded question by default (User Story 1)

1. Upload a small `.txt` knowledge file (see `specs/001-albertos-rag-chatbot/quickstart.md` Scenario 1 for the exact steps) and ask the question it answers:
   ```bash
   curl -s -X POST localhost:8000/api/v1/chat \
     -H 'content-type: application/json' \
     -d '{"question":"<question the uploaded fact answers>"}'
   ```
   **Expected**: `200`, `outcome: "grounded"`, an answer generated by the
   local model — no `LLM_PROVIDER` set anywhere, confirming the default is
   the local backend (spec Acceptance Scenario US1.1).
2. Inspect the corresponding `usage_records` row (e.g. via `psql` or a debug
   query) for that request's `request_id`.
   **Expected**: `provider_kind='llm'`, `provider_name='ollama'`,
   `provider_model='qwen3:4b'` (US1.2).

## Scenario 2 — Switching backends is configuration-only, protections unchanged (User Story 2)

1. Set `LLM_PROVIDER=anthropic` and a real `ANTHROPIC_API_KEY` in `.env`,
   then `docker compose up -d app` (restart only — no rebuild, no code
   change).
2. Repeat Scenario 1's question.
   **Expected**: `outcome: "grounded"` again, but the `usage_records` row
   for this new request now has `provider_name='anthropic'` and
   `provider_model` matching your configured Claude model (US2.1).
3. With `LLM_PROVIDER=ollama` restored, repeat the existing Phase 5 abuse/
   cost scenarios from `specs/001-albertos-rag-chatbot/quickstart.md`
   Scenario 4 (rate limit burst, oversized question, kill switch, budget
   exhaustion) and the Phase 6 prompt-injection scenarios from that
   quickstart's Scenario 5.
   **Expected**: Identical outcomes to what those scenarios already document
   — rate limiting, size limits, the kill switch, budget enforcement, and
   prompt-injection defenses are unaffected by which backend is active
   (US2.2, US2.4).
4. Attempt to influence the backend from the request body:
   ```bash
   curl -s -X POST localhost:8000/api/v1/chat \
     -H 'content-type: application/json' \
     -d '{"question":"<any in-scope question>","provider":"anthropic","model":"claude-opus"}'
   ```
   **Expected**: `400` (unknown fields rejected, per the existing
   `ChatRequest` contract) or, if silently ignored instead, the response is
   generated by whichever backend `LLM_PROVIDER` actually configures —
   never by the client-supplied value (US2.4).
5. With `LLM_PROVIDER=ollama` active, ask several grounded questions, then
   check that the Anthropic budget (`BUDGET_MAX_LLM_REQUESTS_PER_HOUR`) has
   not moved:
   ```bash
   # count rows infra/budget.py would actually count
   psql ... -c "SELECT count(*) FROM usage_records WHERE provider_kind='llm' AND provider_name='anthropic' AND created_at > now() - interval '1 hour';"
   ```
   **Expected**: `0`, regardless of how many Ollama-served requests were made (US2.3).

## Scenario 3 — Ollama unavailable fails safely (Edge Cases)

1. Stop the local backend: `docker compose stop ollama` (or, if using a
   host-run instance, stop it there).
2. Ask any in-scope, previously-grounded question.
   **Expected**: `503`, `outcome: "unavailable"`, the existing generic
   Polish "temporarily unavailable" message — no hostname, port, or stack
   trace in the response body.
3. Check server-side logs:
   ```bash
   docker compose logs app --tail=50 | grep WARNING
   ```
   **Expected**: A warning identifying the Ollama connection failure (mirrors
   the existing `AnthropicLLMProvider` failure-logging pattern), never shown
   to the client.
4. Restart it: `docker compose start ollama`, repeat step 2.
   **Expected**: Back to `200`/`grounded`.

## Scenario 4 — Automatic model provisioning on a fresh environment (User Story 4)

1. Simulate a fresh environment by removing any previously-downloaded model
   data, then start the stack from scratch:
   ```bash
   docker compose down -v          # also removes ollama-data
   docker compose up -d
   ```
2. Watch provisioning happen automatically, with no manual `ollama pull`:
   ```bash
   docker compose logs -f ollama-init
   ```
   **Expected**: Log output shows the configured model (`OLLAMA_MODEL`,
   default `qwen3:4b`) being pulled, then the container exits successfully.
   `docker compose ps ollama-init` shows it as `Exited (0)` — a one-shot
   step, not a long-running service (US4.1).
3. Confirm `app` only became ready after that:
   ```bash
   docker compose ps app
   curl -s -X POST localhost:8000/api/v1/chat -H 'content-type: application/json' \
     -d '{"question":"<an in-scope question>"}'
   ```
   **Expected**: `app` is `Up`/healthy, and the chat request returns a
   normal outcome (`grounded` or `insufficient_information`, not a
   connection error) — the local backend was actually ready by the time
   `app` started (US4.1, spec FR-023).
4. Restart without removing the volume:
   ```bash
   docker compose down
   docker compose up -d
   docker compose logs ollama-init
   ```
   **Expected**: `ollama-init` completes almost immediately, reporting the
   model already present rather than re-downloading it (US4.2, spec
   FR-022).
5. Simulate a provisioning failure with an invalid model name:
   ```bash
   # .env
   OLLAMA_MODEL=this-model-does-not-exist:latest
   docker compose up -d
   docker compose logs ollama-init
   docker compose ps app
   ```
   **Expected**: `ollama-init` exits non-zero and the failure is visible in
   its logs; `app` does **not** start (no container running for it, or it
   stays absent from `docker compose ps`) — no silent fallback to
   Anthropic, no chatbot silently answering as if the local model were
   ready (US4.4, spec FR-028). Restore a valid `OLLAMA_MODEL` afterward and
   `docker compose up -d` again to recover.

## Scenario 5 — Compare both backends on the same evaluation set (User Story 3)

```bash
# Run 1: local backend (default)
uv run python scripts/run_eval.py

# Run 2: paid backend
# (set LLM_PROVIDER=anthropic in .env, docker compose up -d app)
uv run python scripts/run_eval.py
```

**Expected**: Both runs execute the same 30 questions from
`eval/questions.jsonl` unmodified; each run's printed report identifies
which backend (`LLM_PROVIDER`) produced it, and the two reports' pass/fail
and metric tables (grounded accuracy, false-grounded rate, etc. — see
`eval/README.md`) can be compared side by side.

## Automated verification

```bash
uv run pytest tests/unit/test_ollama_provider.py -v
uv run pytest    # full suite — must pass with NO Ollama process running anywhere
```

**Expected**: `OllamaLLMProvider`'s own tests pass using a mocked HTTP
transport; the full suite passes with zero real Ollama calls and zero real
Anthropic calls, exactly like the existing suite already guarantees for
Anthropic (Principle XI) — confirm by running with the `ollama` container
stopped.
